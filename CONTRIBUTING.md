# Contributing to Project Resonance

Thank you for your interest in contributing to Project Resonance.

Project Resonance is developed with the same care and discipline used in professional software engineering projects. Every contribution should support the project's mission:

> **Help guitarists spend less time configuring equipment and more time creating music.**

---

# Our Philosophy

Project Resonance is built on collaboration, thoughtful decision-making, and continuous improvement.

We believe that:

- Great software begins with understanding the problem.
- Documentation is a first-class deliverable.
- Simplicity is usually the best solution.
- User experience is as important as functionality.
- Every contribution should improve the product.

---

# Before Contributing

Before beginning work:

1. Read the README.
2. Read the Getting Started guide.
3. Review the Product Bible.
4. Review any relevant Product Standards.
5. Review existing Design Decision Logs (DDL) and Architectural Decision Records (ADR).

Understanding previous decisions helps keep the product consistent.

---

# Types of Contributions

Contributions may include:

- Documentation improvements
- User experience ideas
- Wireframes
- Product discussions
- Design reviews
- Bug reports
- Feature implementation
- Code improvements
- Testing
- Accessibility improvements

Every contribution is valuable.

---

# Our Development Process

Project Resonance follows an iterative development process.

Ideas generally move through these stages:

1. Discussion
2. Documentation
3. Review
4. Approval
5. Implementation
6. Validation
7. Release

Whenever practical, decisions should be documented before implementation.

---

# The Resonance Test

Before proposing a new feature, ask:

> **Does this make it easier to create music?**

If the answer is uncertain, revisit the idea before implementing it.

The best features reduce friction rather than add capability for its own sake.

---

# Coding Philosophy

When implementation begins, code should strive to be:

- Simple
- Readable
- Maintainable
- Testable
- Well documented

Future contributors should be able to understand the code without unnecessary complexity.

---

# Documentation Standards

Documentation should:

- Explain why decisions were made.
- Link to related documents.
- Stay current.
- Use clear, concise language.
- Be reviewed when significant changes occur.

---

# Git Guidelines

Commit messages should:

- Use the imperative mood.
- Describe one coherent unit of work.
- Be concise.
- Be meaningful.

Examples:

- Create project glossary
- Add Product Bible cover
- Document mission and vision
- Update Tone Studio wireframe

---

# Code Reviews

Reviews should focus on improving the product rather than criticizing contributors.

Feedback should be:

- Respectful
- Specific
- Constructive
- Actionable

Every review is an opportunity to improve both the product and the team's shared understanding.

---

# Decision-Making

When faced with multiple good solutions, prefer the one that:

- Protects the creative flow.
- Reduces cognitive load.
- Feels more like an instrument.
- Simplifies the user's experience.
- Is easier to maintain over time.

Good decisions compound over the life of a product.

---

# Thank You

Every contribution—whether a new feature, documentation improvement, bug fix, or design suggestion—helps Project Resonance become a better companion for musicians.

Thank you for being part of the journey.
